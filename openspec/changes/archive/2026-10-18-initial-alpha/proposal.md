# Prepare the first FAIR Guide alpha

## Why

Researchers, data stewards, repository administrators and communities need practical, source-backed FAIR guidance
and honest self-assessment. The locally implemented Guide needs one verified candidate and an explicit delivery
hand-off before its first official alpha.

## What Changes

- Deliver the bilingual life-cycle path, catalogue, principle explorer, helpers, self-checks and scoped evidence.
- Keep one knowledge model for the page, RO-Crate and static API, with locally owned compact catalogue identities.
- Preserve original source passages and assessment scope, manual answers and complete portable evidence.
- Finish mobile/catalogue presentation, useful editorial hints, truthful coverage and bounded code hygiene.
- Provide repository-owned capability specs, contributor tooling and a final release/operator checklist.

## Capabilities

### New Capabilities

The five installed `fair-guide/guide-*` specifications describe the initial product. Their active change copies
record the same reviewed contracts and are kept consistent until the completed change is archived.

### Modified Capabilities

- `fair-guide/guide-knowledge-base`: compact Guide-owned identity and record metadata.
- `fair-guide/guide-experience`: ranked linking hints, bounded lists and readable mobile interaction.
- `fair-guide/guide-self-check`: self-assessment and retained evidence.
- `fair-guide/guide-live-checks`: explicit, scoped external lookups and local tests.
- `fair-guide/guide-delivery`: checked artifacts, trusted workflows and explicit publication gates.

## Impact

The first release establishes the identifier baseline. Unreleased route compatibility is removed; supported saved
result formats remain loadable. Production comes from release artifacts; the default branch supplies `/next/`.
No remote delivery, privileged configuration, tag, release or archive follows automatically from local completion.
